## 2. Native volume/mute: node Props versus device Route

The SPA `Props` object defines scalar `volume` (float), `mute` (bool), `channelVolumes` (array of float), `monitorVolumes`, `monitorMute`, `softVolumes`, `softMute`, `channelMap`, and `params`. The latter are different controls, **not** interchangeable mirror fields. `soft*` is explicitly software-applied; `channelVolumes` is per-channel linear gain; `monitorVolumes` affects the monitor path rather than ordinary speaker gain. Inspect the actual `Props` and `PropInfo` capabilities before enabling controls, not merely a `media.class` guess ([SPA `props.h:62-113`](https://docs.pipewire.org/props_8h_source.html#l62), [node listener/enum API](https://docs.rs/crate/pipewire/0.10.1/source/src/node.rs)). A playback stream's own `Props` is a natural target for its stream strip; local media playback even calls `stream.set_control` for its **own** channelVolumes/mute ([local `pipewire.rs:385-390`](../../../../repos/sekka/desktop/aizome/crates/aizome-media/src/pipewire.rs)).

A physical ALSA/BlueZ endpoint can have volume controlled at its **Device `Route`** rather than its Node `Props`: route object has `index`, logical `device` (not PipeWire global ID), `direction`, `profiles`, nested `props: SPA_TYPE_OBJECT_Props`, and `save`. Enumerate the active Route and preserve its `(index,device)` while setting its nested `channelVolumes`/`mute`; do not overwrite a whole Route with just a `Props` pod or infer its logical-device index from the route index ([SPA `route-types.h:25-39`](https://docs.pipewire.org/route-types_8h_source.html#l25)). WirePlumber `device.restore-routes` remembers manually changed routes **including sink/source volume**, and ALSA `api.alsa.soft-mixer=true` disables hardware mixer while software volume remains available ([WirePlumber settings, `device.restore-routes`](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html#device-restore-routes), [ALSA options](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html#device-properties)). **[INFERENCE]** Route volume/mute is policy-owned for ordinary hardware; coordinate writes through WirePlumber `mixer-api` or the existing Pulse API to preserve restoration and avoid hardware/software double application.

`pwvucontrol` is a particularly valuable **counterexample to naïve native Node-Props-only mixing**: it uses Rust **WirePlumber bindings** `mixer-api` `get-volume`/`set-volume`, receiving a map with `volume`, `mute`, and indexed `channelVolumes`, and preserving channel ratios when moving the overall slider. Thus it delegates route/node selection to policy, while separately writing `Props.volume` for a low-level main-volume control and `Props.monitorVolumes` for monitor volume; its device code writes `Profile`/`Route` directly for profile/route selection ([`mixerapi.rs:122-254`](https://github.com/saivert/pwvucontrol/blob/main/src/backend/pwnodeobject/mixerapi.rs#L122-L254), [`pwnodeobject.rs:390-508`](https://github.com/saivert/pwvucontrol/blob/main/src/backend/pwnodeobject.rs#L390-L508), [`pwdeviceobject.rs:228-249,381-404`](https://github.com/saivert/pwvucontrol/blob/main/src/backend/pwdeviceobject.rs#L228-L249)). `wpctl set-volume`/`set-mute` acts on a node's audio stream(s); route selection has its own `get-route/set-route` commands ([wpctl manual, set-volume/get-route](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html#set-volume)). Pavucontrol's path here is via pipewire-pulse, exactly the translation the existing Sekka `audio.rs:4-23` relies on; it is not evidence that pavucontrol itself calls native Node `set_param`.

**Scale matters.** SPA channelVolumes are **linear amplitude**, while a user-facing Pulse/WirePlumber slider may be a *cubic* perceptual control. WirePlumber's documented default sink route volume is `0.4 ^ 3`, explicitly called 40% cubic scale ([WirePlumber `device.routes.default-sink-volume`](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html#device-routes-default-sink-volume)). Existing Sekka `audio.rs` reports Pulse fractions as `Volume/NORMAL`, not raw SPA amplitude ([local `audio.rs:42-43,448-479`](../../../../repos/sekka/desktop/aizome/crates/aizome-sys/src/audio.rs)). **[INFERENCE]** For a cubic UI: `gain = ui^3`, `ui = cbrt(max(gain,0))`, amplitude dB `20*log10(gain)` (zero = −∞); for balance preserve the loudest channel then attenuate channels on the opposite side rather than assigning `volume` and destroying ratios. Compare reference's channel-preserving algorithm ([pwvucontrol `send_volume_using_mixerapi`](https://github.com/saivert/pwvucontrol/blob/main/src/backend/pwnodeobject/mixerapi.rs#L130-L181)); Sekka's Pulse balance uses libpulse channel-map-aware `set_balance` ([local `audio.rs:1317-1345`](../../../../repos/sekka/desktop/aizome/crates/aizome-sys/src/audio.rs)). Do **not** silently label direct SPA linear 0.5 as the same perceived “50%” as an existing Pulse slider.

**Concrete 0.10.1 SPA construction recipe (proposed integration, not claimed tested code):** `spa::pod::{Value,Object,Property,ValueArray,Pod}` and `spa::pod::serialize::PodSerializer` are the same serialization mechanism already used in [local `pipewire.rs:351-367`](../../../../repos/sekka/desktop/aizome/crates/aizome-media/src/pipewire.rs); `Property::new(u32,Value)`, `Value::Object`, `Value::ValueArray(ValueArray::Float(...))` are present in [libspa 0.10.1 `pod/mod.rs:2952-3098`](https://docs.rs/crate/libspa/0.10.1/source/src/pod/mod.rs#L2952-L3098). Both proxies have `set_param(id: spa::param::ParamType, flags: u32, param: &Pod)` and `subscribe_params(&[ParamType])`, with W+X required for a write ([node.rs `Node::set_param`](https://docs.rs/crate/pipewire/0.10.1/source/src/node.rs), [device.rs `Device::set_param`](https://docs.rs/crate/pipewire/0.10.1/source/src/device.rs)). ## 3. Defaults and moving streams

Bind the metadata global named `default`: subject **0** keys `default.audio.sink`/`default.audio.source` are effective choices and `default.configured.audio.sink`/`.source` are explicit choices. WirePlumber documents `Spa:String:JSON` values such as `{"name":"the-node-name", "stream":"the-port-group"}`; `stream` is optional and particularly relevant to multistream nodes. It chooses configured default if available, else priority/availability-selected best target; `wpctl set-default` remembers chosen default across restarts, `clear-default` removes it ([WirePlumber linking introduction/default example](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html#introduction), [wpctl set-default](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html#set-default)). **[INFERENCE]** UI should show effective versus user-configured separately and target by stable node name, not ephemeral global number; do not invent an implicit configured choice if only effective key exists.

Per-stream **`target.object`** may be a stream node property at creation or a `default` metadata entry with the **stream node's global ID as subject** to move it at runtime. The metadata value is target `node.name` or `object.serial` (not an arbitrary Pulse sink index), with WirePlumber's `linking.allow-moving-streams=true`; `node.dont-move` disables this. For multiple port groups there is `target.stream.<port-group>` metadata with structured JSON; plain target.object chooses first suitable target stream. [WirePlumber linking, stream properties](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html#stream-node-linking-properties), [settings `linking.allow-moving-streams`](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html#linking-allow-moving-streams). In current pwvucontrol, dropdown calls `set_default_target`, which writes both legacy `target.node` (node ID) and `target.object` (`Spa:Id`, target serial) to metadata; its reset writes `-1` for both ([`stream_dropdown.rs:130-162`](https://github.com/saivert/pwvucontrol/blob/main/src/ui/stream_dropdown.rs#L130-L162), [`pwnodeobject.rs:~500-590`](https://github.com/saivert/pwvucontrol/blob/main/src/backend/pwnodeobject.rs)). Avoid copying deprecated `target.node`: WirePlumber explicitly recommends `target.object` ([settings, linking.allow-moving-streams](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html#linking-allow-moving-streams)). Pavucontrol calls Pulse's `move_sink_input`/`move_source_output` through pipewire-pulse; existing Sekka already calls both ([local `audio.rs:1286-1291`](../../../../repos/sekka/desktop/aizome/crates/aizome-sys/src/audio.rs)). **[INFERENCE]** A native move command writes `metadata.set_property(stream_id,"target.object",Some("Spa:Id"),Some(serial_string))` for observed `object.serial`, or JSON/string when using a stable `node.name` according to binding/server behavior; verify the resulting metadata and actual Link, report rejected `node.dont-move` rather than optimistically declaring movement. The Rust metadata API and permission conditions are recorded in [r1 §6](r1-graph.md#6-pipewire-rs-010x-api-and-ownership).

## 4. Profiles and routes

A PipeWire **Device** publishes `EnumProfile` (choices) and `Profile` (current), `EnumRoute` and `Route`; subscribe to current params and re-enumerate choices on change. Profile `index/name/description/priority/available/classes/save`; Route `index/direction/device/name/description/priority/available/profiles/props/save`. `available` is an SPA enum, not simply a boolean until normalized to yes/no/unknown. `profiles` constrains valid route choices. `wpctl get-profile/set-profile` uses a **profile index**; `get-route/set-route` uses a **route index**, and get-route can scope to node's logical device ([SPA `profile-types.h:24-33`](https://docs.pipewire.org/profile-types_8h_source.html#l24), [SPA `route-types.h:25-39`](https://docs.pipewire.org/route-types_8h_source.html#l25), [wpctl profile and route commands](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html#get-profile)). Pwvucontrol enumerates these four params; sets Profile object `{index,save:true}` and Route `{index,device,save:true}` ([`pwdeviceobject.rs:115-249,251-404`](https://github.com/saivert/pwvucontrol/blob/main/src/backend/pwdeviceobject.rs#L115-L404)). The logical `device` index comes from the node's `device_index()` there, **not** its PipeWire registry ID ([`pwnodeobject.rs` `set_route`](https://github.com/saivert/pwvucontrol/blob/main/src/backend/pwnodeobject.rs)).

ALSA WirePlumber monitor creates card-like Devices and node-like logical endpoints, using ACP/UCM profiles/ports; switching a card profile can replace its nodes/ports. `Pro Audio` is a profile offered by ACP on suitable interfaces, exposing raw multichannel paths rather than ordinary stereo consumer routes; **[INFERENCE]** do not assume every card has it, nor that all its AUX channels are stereo pairs. Rebind affected nodes and remove obsolete meter/link bindings after a profile change rather than keeping stale IDs. [WirePlumber ALSA card/node and profile configuration](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html), [r1 graph grouping §4](r1-graph.md#4-implementable-matrix-grouping-and-labels). BlueZ headset profiles may switch from music to headset when capture starts under WirePlumber autoswitch, so show active profile as externally mutable and offer a warning that selecting it changes running endpoints ([WirePlumber `bluetooth.autoswitch-to-headset-profile`](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html#bluetooth-autoswitch-to-headset-profile)). **[INFERENCE]** For simple Settings reuse Pulse `set_card_profile`/`set_sink_port`; for full native graph/device page use Device param subscription, route's `profiles` and actual current logical `device` index, and explicit `save=true` for requested persistence. Do not equate ACP hardware route with graph Port.

## 5. Peak metering versus profiler

Pavucontrol-style peak detect is a **capture stream** receiving reduced-rate peak samples, not a periodically queried Node volume. Existing Sekka uses Pulse's `PEAK_DETECT` record stream at 25 Hz on a source or `.monitor` sink ([local `meter.rs:97-137`](../../../../repos/sekka/desktop/aizome/crates/aizome-sys/src/meter.rs)). Pwvucontrol's Rust implementation instead constructs a native `StreamRc` per `LevelbarProvider`: `Direction::Input`, `Some(id)` target, `resample.peaks=true`, `stream.monitor=true`, `node.passive=true`, `node.rate=node.latency=1/25`, mono F32 format at 144 Hz; uses `AUTOCONNECT|MAP_BUFFERS|RT_PROCESS|DONT_RECONNECT`, processes dequeued float peaks and disconnects on Drop. This is a concrete native implementation, but its `PEAK_RATE=144` and `node.rate=1/25` differ, so don't infer a guarantee of precisely 25 callbacks/s from it ([pwvucontrol `levelprovider.rs:1-150`](https://github.com/saivert/pwvucontrol/blob/main/src/ui/levelprovider.rs#L1-L150)). `stream.capture.sink=true` is an alternative **capture-sink** property to use when targeting an output sink; `target.object` addresses node name/serial, and `node.passive` avoids a monitor keeping a device active unnecessarily; `stream.monitor=true` is what the observed pwvucontrol meter actually sets. **[INFERENCE]** Test `stream.capture.sink` versus `stream.monitor` with the intended sink/source roles and available PipeWire version before finalizing, and use one explicit policy-target mode rather than redundantly assuming both flags mean the same thing. `StreamFlags::AUTOCONNECT` and `DONT_RECONNECT` plus `Direction::Input` and target ID are grounded in that reference.

**Cost model [INFERENCE].** A meter costs a graph stream, its buffers/links, low-rate peak reduction and an event/callback per interval; `resample.peaks` avoids copying full 48-kHz PCM to UI, but N meters still mean N graph nodes/links and N callbacks. Naïvely multiplying `aizome-sys::Meter` also multiplies OS threads/Pulse connections. One native backend loop can own multiple `StreamRc`s, with RT callbacks doing only peak reduction/atomic writes and UI polling **visible** levels at ~20–30 Hz; avoid allocations/logging, locks and GUI wake on each RT callback. Sample only displayed/selected strips (e.g. 8–16 visible, configurable cap), detach/stop streams when hidden, when node disappears or core disconnects; reuse Settei's `hidden()` cleanup model ([local `sound.rs:302-340`](../../../../repos/sekka/desktop/aizome/apps/settei/src/panes/sound.rs)). Also avoid introducing a fake recording application: existing classifier excludes peak detect by name/resample method ([local `audio.rs:898-916`](../../../../repos/sekka/desktop/aizome/crates/aizome-sys/src/audio.rs)). **[INFERENCE]** Name our own meter accurately (`application.name=Aizome`, `media.name=Aizome peak meter`) and filter by `application.id`/stream purpose rather than pwvucontrol's deliberate pavucontrol impersonation ([pwvucontrol meter properties](https://github.com/saivert/pwvucontrol/blob/main/src/ui/levelprovider.rs#L36-L56)).

`pw-top` is **not** an audio amplitude meter. It consumes the optional `libpipewire-module-profiler`/Profiler object to display graph driver/follower QUANT, RATE, WAIT, BUSY, W/Q, B/Q, ERR (xrun+error count), FORMAT; driver quantum/rate yields period duration, e.g. 1024/48000=21.3ms. A profiler may collect every cycle by default; `profile.interval.ms` can reduce sampling overhead. It does not provide per-strip peaks ([profiler module](https://docs.pipewire.org/page_module_profiler.html), [pw-top columns and ERR](https://docs.pipewire.org/page_man_pw-top_1.html)). Coppwr includes a separate profiler page; qpwgraph and Helvum are connection canvases, not an audio amplitude source ([Coppwr README Features](https://github.com/dimtpap/coppwr#features), [r1 §3](r1-graph.md#3-existing-patchbays-and-cli-behavior)). EasyEffects' plugin list includes *Level meter*, based on libebur128 dependency: that is effect-chain signal analysis, not free server-wide peaks for arbitrary third-party strips ([EasyEffects README Effects/Dependencies](https://github.com/wwmm/easyeffects#effects-available), [filter-chain EBU R128 filter](https://docs.pipewire.org/page_module_filter_chain.html#ebur128-filters)). **[INFERENCE]** Offer optional diagnostics as a different feature from peak bars; never use `pw-top ERR` as if it were a clipping indicator.

## 6. Graph settings, latency, xruns and tools

PipeWire's daemon exposes a `settings` Metadata object. `pw-metadata -n settings 0 clock.force-quantum 256` writes subject **0** key `clock.force-quantum` with value `256` at runtime; it forces the graph's quantum, **not** each client's ALSA hardware period size and **not** a persisted `pipewire.conf` edit. Set it to `0` to restore variable quantum. `clock.force-rate=RATE` forces graph rate and running streams resample, `0` releases it. Other documented runtime keys: `clock.rate`, `clock.allowed-rates`, `clock.quantum`, `clock.min-quantum`, `clock.max-quantum`. Runtime changes can bypass configured restrictions unless `settings.check-quantum`/`settings.check-rate` are set; static `default.clock.*` goes in daemon config/drop-ins. ([PipeWire daemon runtime settings](https://docs.pipewire.org/page_man_pipewire_1.html#runtime-settings), [config default clocks and checks](https://docs.pipewire.org/page_man_pipewire_conf_5.html#context-properties)). **[INFERENCE]** Show effective graph rate/quantum next to force overrides, allow Restore Auto, and distinguish system default versus temporary session override. Subscribe to `settings` metadata and disable editing when absent/no write permission.

`quantum/rate` is **processing period**, not round-trip latency. `pw-top` explains followers may suggest a quantum/rate, driver selects graph values, and a different negotiated device/stream sample rate triggers resampling ([pw-top QUANT/RATE](https://docs.pipewire.org/page_man_pw-top_1.html)). `node.latency` is a client scheduling suggestion, used by Sekka's own playback and computed as frames/rate; it need not equal measured input-to-output delay ([local `pipewire.rs:5-14,26-34,286-301`](../../../../repos/sekka/desktop/aizome/crates/aizome-media/src/pipewire.rs)). `ProcessLatency` reports additional internal processing delay and is adjustable at runtime via `pw-cli e/s <node> ProcessLatency`, as documented by WirePlumber's ALSA page ([ALSA process latency](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html#node-properties)). **[INFERENCE]** UI should label `256/48000 = 5.33 ms` as *one graph period*, not “total latency”; if no measured path latency available, report unknown rather than promising a round-trip number.

The Profiler object/`pw-top` ERR counts xruns and errors; a driver xrun may be deadline overrun or hardware, follower xrun misses graph cycle; `pw-top c` resets **that instance's displayed counters**, not global server totals ([pw-top ERR/commands](https://docs.pipewire.org/page_man_pw-top_1.html)). **[INFERENCE]** Maintain a sampled per-node diagnostic delta/epoch and label it `xrun/errors`, never claim a Node `driver` property alone is a readable counter (it is a scheduling capability). Stop profiler subscription outside diagnostics if it is costly.

## 7. Effects: filter-chain, hosting and an achievable first page

`libpipewire-module-filter-chain` runs a declared DSP graph with a **capture stream and playback stream**; session policy can connect those automatically. Graph has `nodes` (`type`, `name`, `plugin`, `label`, `config`, `control`), `links` from `node:port` to `node:port`, external `inputs`/`outputs`, optional capture/playback volume mappings. LADSPA, LV2, optional SOFA, FFmpeg and builtins are supported; plugin format/runtime optionality depends on packaging. Builtins include `mixer` (up to 8 inputs with gains), `copy`, `bq_peaking`, `bq_lowshelf`, `bq_highshelf`, low/high/bandpass/notch/allpass, `convolver`, `delay`, `invert` and more; filter-chain docs specify their ports and controls ([official filter-chain Nodes/Links/Inputs/Volumes/Builtins](https://docs.pipewire.org/page_module_filter_chain.html#filter-graph-description)). A filter graph's **internal** nodes/links are not automatically separately exposed as PipeWire registry globals; its two streams are the external graph objects ([module architecture](https://docs.pipewire.org/page_module_filter_chain.html)).

Official Dolby virtual-sink example (excerpt, retaining literal config semantics):

```ini
context.modules = [
 { name = libpipewire-module-filter-chain
   args = {
     node.description = "Dolby Surround Sink"
     filter.graph = {
       nodes = [ { type = builtin name = mixer label = mixer
                   control = { "Gain 1" = 0.5 "Gain 2" = 0.5 } }
                 { type = ladspa name = enc plugin = surround_encoder_1401 label = surroundEncoder } ]
       links = [ { output = "mixer:Out" input = "enc:S" } ]
       inputs = [ "enc:L" "enc:R" "enc:C" null "mixer:In 1" "mixer:In 2" ]
       outputs = [ "enc:Lt" "enc:Rt" ]
     }
     capture.props = { node.name = "effect_input.dolby_surround" media.class = Audio/Sink
                       audio.channels = 6 audio.position = [ FL FR FC LFE SL SR ] }
     playback.props = { node.name = "effect_output.dolby_surround" node.passive = true
                        audio.channels = 2 audio.position = [ FL FR ] }
   }
 }
]
```

The quoted graph and stream property structure is from [PipeWire's Dolby virtual sink example](https://docs.pipewire.org/page_module_filter_chain.html#example-configuration-of-a-dolby-surround-encoder-virtual-sink), edited here only to omit `media.name` and comments for space. Its RNNoise virtual **source** example reverses media.class placement: passive capture on real input, `Audio/Source` playback exposed to recording apps ([official virtual source example](https://docs.pipewire.org/page_module_filter_chain.html#example-configuration-of-a-virtual-source)). **[INFERENCE]** For first EQ effect, use two peaking biquad nodes (left/right), or one node duplicated by the module's documented channel duplication when `inputs`/`outputs` omitted; set `Freq`, `Q`, `Gain`, explicit stereo capture sink and passive playback stream; preserve both channels and expose bypass as safe routing/chain activation rather than claiming a hidden parameter exists. Multi-band EQ requires multiple bq nodes with per-channel links; `copy` for fanout, `mixer` for fan-in ([filter-chain links/biquads](https://docs.pipewire.org/page_module_filter_chain.html#biquads)).

**Runtime controls.** Initial values go in each graph node's `control={ "Freq"=… "Q"=… "Gain"=… }`; the node-level SPA `Props` supports `params`, and filter-chain control addressing convention is `"<node>:<control>"` (e.g. `eq:Freq`). **[INFERENCE]** A native `set_param(Props)` containing a `SPA_PROP_params` structured value on the appropriate exposed filter stream should allow runtime adjustment, but this exact nested POD shape and target stream were **not** established by an inspected 0.10.1 code example; do not ship generated runtime-control writes from this report alone. Use a scratch non-production chain to inspect `pw-cli enum-params <node> Props` and test `pw-cli set-param <node> Props …`, then read back observed `Props`/audibly compare; do not represent an invented `params` array syntax as tested. The documented biquad controls and runtime-adjustable `bq_raw` coefficients are grounded ([filter-chain Biquads](https://docs.pipewire.org/page_module_filter_chain.html#biquads), [SPA `SPA_PROP_params`](https://docs.pipewire.org/props_8h_source.html#l112)). For an initial robust release, replacing a generated config and restarting **only the dedicated chain process** on changed presets is valid but interrupts that chain briefly; it does not require guessed live POD serialization **[INFERENCE]**.

**Lifetime/persistence are four different decisions:**

1. A `~/.config/pipewire/pipewire.conf.d/aizome-*.conf` fragment appends `context.modules` at **daemon startup**. Creating/editing it alone does nothing until daemon restart; a module failure can affect daemon startup or its logs. `filter-chain.conf.d/` fragments apply to an invocation using `filter-chain.conf`, **not** automatically to the already-running main daemon; official examples say `pipewire -c filter-chain.conf` or put it under `pipewire.conf.d/` to run inside server ([config lookup/drop-ins](https://docs.pipewire.org/page_man_pipewire_conf_5.html#drop-in-configuration-files), [filter-chain example instructions](https://docs.pipewire.org/page_module_filter_chain.html#example-configuration-of-a-virtual-source)). Avoid modifying a user's unrelated fragments.
2. `pw-cli load-module libpipewire-module-filter-chain …` loads in **pw-cli's own local context**, not remotely into the daemon; one-shot `pw-cli …` exits and loses module/node ownership. Interactive pw-cli retains it while the process runs. This is explicitly documented, and using a one-shot load as persistent provisioning is incorrect ([pw-cli MODULE MANAGEMENT](https://docs.pipewire.org/page_man_pw-cli_1.html#module-management)).
3. `pw_context_load_module` / `context.load_module` in **our own** context similarly lives with our app process; quitting GUI removes effects. **[INFERENCE]** This can suit preview but is surprising for a persisted system-wide effects preset. Module creation/connection failure needs feedback and teardown, not a success toast just because load was requested ([pw-cli local-context ownership](https://docs.pipewire.org/page_man_pw-cli_1.html#module-management), [PipeWire context/module API](https://docs.pipewire.org/group__pw__context.html)).
4. A **dedicated helper/service** running `pipewire -c filter-chain.conf` with app-generated isolated configuration, supervised under a user's service manager, decouples DSP lifetime from GUI. **[INFERENCE]** Persist an explicit enabled flag + generated config atomically, start/stop helper on enable/disable, observe its status and expected filter nodes, and never auto-restart endlessly on invalid plugin/config; restarting PipeWire or WirePlumber may temporarily remove its streams and trigger reconnection. A helper has startup/crash/log/upgrade concerns but does not require restarting the main sound daemon; service persistence requires a separately enabled user service, not merely writing a file ([PipeWire filter example](https://docs.pipewire.org/page_module_filter_chain.html#example-configuration-of-a-virtual-source), [pw-cli process locality](https://docs.pipewire.org/page_man_pw-cli_1.html#module-management)).

EasyEffects is an **audio processor**, not a remote `filter-chain` front end: its README says old GStreamer was replaced by *native PipeWire filters*, lists reorderable EQ/compressor/convolver/limiter/level meter and external plugin dependencies including LSP/Calf/libebur128. Its virtual processing sink/source are commonly named `easyeffects_sink` and `easyeffects_source` **[INFERENCE: names need version check]**; importantly EasyEffects warns **not** to set its virtual devices as default, preferring hardware default ([EasyEffects README History/Effects/Warning](https://github.com/wwmm/easyeffects#readme)). **[INFERENCE]** Presets describe effect order and parameters, with plugin availability/version dependencies; do not attempt to edit its files as our effect protocol. Carla is a separate **JACK/PipeWire client plugin host** with LADSPA/LV2 et al, a rack/patchbay and JACK single-client/multi-client modes; connect its externally visible ports but don't claim Aizome owns its instances/presets ([Carla manual Basic Concepts/Engine modes](https://kx.studio/Documentation:Manual:Carla)).

**Recommendation [INFERENCE]:** First Effects page lists discoverable external effect nodes read-only and manages one named stereo *parametric EQ virtual sink* using built-in biquads in a dedicated helper, explicit output hardware target/auto policy, enable/disable, saved bands, bypass and honest status (running/failed/missing target). Persist only Aizome-generated config under its own namespace and restart its helper on changes until a tested runtime POD control path exists. Warn if changing default or moving streams would affect other apps; do not auto-override default silently. Later: live control, per-chain input/output routing, convolution/sofa (file handling and latency), LADSPA/LV2 inventory/hosting (plugin scanning, realtime safety, state/presets, crash isolation). FFmpeg filtergraph docs explicitly warn it is **not RT safe** and recommend async `node.async=true` ([filter-chain FFmpeg section](https://docs.pipewire.org/page_module_filter_chain.html#ffmpeg)); don't offer arbitrary FFmpeg DSP inside the RT graph as a safe default.

## 8. Client identity, permissions, restart and ownership

Set context/stream identity `application.name=Aizome`, `application.id=org.sekka.Aizome`, honest icon/process descriptions, `media.category=Manager` for a manager-only client when appropriate; for an actual meter capture stream specify capture role/purpose rather than labeling capture as `Manager`. Aizome's Pulse service already sets application name/id and its native playback sets application name/id, `media.category=Playback` ([local `audio.rs:957-968`](../../../../repos/sekka/desktop/aizome/crates/aizome-sys/src/audio.rs), [local `pipewire.rs:290-301`](../../../../repos/sekka/desktop/aizome/crates/aizome-media/src/pipewire.rs), [PipeWire key names](https://docs.pipewire.org/group__pw__keys.html)). `node.dont-reconnect=true` is meaningful on intentionally pinned ephemeral meter streams and **not** something to set on third-party streams or a resilient effect blindly; WirePlumber documents it can inhibit target fallback after removal ([WirePlumber stream properties](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html#stream-node-linking-properties)). `node.passive=true` reduces accidental device activation for a monitoring stream ([pwvucontrol meter properties](https://github.com/saivert/pwvucontrol/blob/main/src/ui/levelprovider.rs#L36-L56)). Never spoof pavucontrol application ID to hide our meters: pwvucontrol does so explicitly and that is not identity hygiene ([same source](https://github.com/saivert/pwvucontrol/blob/main/src/ui/levelprovider.rs#L36-L56)).

Native operations require object-specific permissions: `Node::set_param` and `Device::set_param` require W+X; `subscribe_params` needs X, metadata set needs metadata W+X plus subject M; a discovered registry global need not be writable. Surface permission errors/readonly controls; do not assume a bound proxy grants control merely because `enum_params` returned data ([pipewire-rs 0.10.1 Node](https://docs.rs/crate/pipewire/0.10.1/source/src/node.rs), [Device](https://docs.rs/crate/pipewire/0.10.1/source/src/device.rs), [Metadata](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/metadata/struct.Metadata.html)). Flatpak permissions are outside this desktop target.

**[INFERENCE]** A manager backend should register Core `.error` and `.done` listeners, use a sync roundtrip only as initial-enumeration completion (not as a claim that policy has linked everything), detect broken core/mainloop, send `Unavailable` and increment epoch, drop all old proxies/listeners/meter streams, create a new context/core/registry and reenumerate metadata/devices/nodes; back off between retries and fail outstanding commands. Do not carry old global IDs across reconnect. The established ownership/thread channels are in [r1 §6](r1-graph.md#6-pipewire-rs-010x-api-and-ownership), while Sekka's Pulse analogue explicitly resets/fails queued tasks/retries ([local `audio.rs:920-948`](../../../../repos/sekka/desktop/aizome/crates/aizome-sys/src/audio.rs)). Filter helper and core can restart independently; distinguish “effect process exited,” “PipeWire disconnected” and “target missing” rather than reporting all as muted. A module running in our own context dies with us; a daemon fragment loads at daemon start; an enabled supervised helper may restart independently as configured ([pw-cli module ownership](https://docs.pipewire.org/page_man_pw-cli_1.html#module-management), [config drop-ins](https://docs.pipewire.org/page_man_pipewire_conf_5.html#drop-in-configuration-files)).
