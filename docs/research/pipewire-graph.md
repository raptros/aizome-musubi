# PipeWire graph research for Aizome's patch matrix

Scope: connections, discovery, naming and grouping only; not mixer/effects. Version references distinguish PipeWire 1.2, 1.4, 1.6 and the separately published Rust binding 0.10.1. A **PipeWire port** is not a PulseAudio/ACP card *route* (also called a “port” in PulseAudio). Evidence below is from upstream documentation and inspected implementation, not a measurement on a running production installation. Proposed policy is marked **[INFERENCE]**. Sources are linked inline by section/function or source-line anchors and collected at the end.

## 1. Object model and property inventory

A registry global has an ID, type, version, permissions and optional property dictionary. Registry events expose existence and initial properties; binding typed proxies supplies detailed info and change events. The useful object families are **Client** (connection/application), **Device** (card, camera, Bluetooth adapter endpoint), **Node** (processing endpoint/stream), **Port** (directional endpoint of a node), **Link** (output port → input port), **Metadata** (subject/key/value policy state), **Factory** (constructor, notably `link-factory`) and **Module** (server-side module). Only Node/Port/Link form the actual connectable graph; the rest explain origin, targeting and capabilities. Devices can own multiple nodes; ALSA card roughly corresponds to Device, ALSA PCM roughly to Node; profiles may recreate the nodes. See [PipeWire object/property reference](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#description), [WirePlumber ALSA configuration](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html#alsa-configuration), [Rust registry global type](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/registry/struct.GlobalObject.html).

**Guarantee discipline.** Registry-global `id` and `type_` are structural; `global.props` itself is `Option`, so **none of the named dictionary keys is universally guaranteed**. Node/Port/Link info objects have structural IDs and (for Port/Link) typed direction/endpoints; `info.props()` remains optional. Conventional producers populate the keys described below, but robust rendering must retain an anonymous numeric-ID fallback, tolerate missing/out-of-order parents and merge subsequent info. Helvum assumes `node.id` on a port and panics if absent—an example of convention rather than a global schema guarantee. References: [Rust registry GlobalObject](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/registry/struct.GlobalObject.html), [Helvum `handle_port_info`](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L333-L405), [qpwgraph `qpwgraph_registry_event_global`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L414-L529).

`object.serial` is a 64-bit identity for one incarnation and `object.path` an optional object path; neither promises stable identity after graph restart. Global IDs can be recycled. For persisted routing, prefer meaningful `device.name`/hardware serial + `node.name` + `port.name` and direction, with ambiguity detection, not `object.serial` alone. On current-runtime attach use global IDs; `target.object` can accept current `object.serial` or `node.name`. [Key Names](https://docs.pipewire.org/group__pw__keys.html), [node session-manager properties](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#session-manager-properties), [pw-link port specifications](https://docs.pipewire.org/page_man_pw-link_1.html#connecting-ports).

Physical output/capture naming reverses everyday speaker terminology: a microphone capture node's `capture_FL` is an **output port** (matrix row); speaker playback node's `playback_FL` is an **input port** (column). Node `Audio/Sink` has input, `Audio/Source` has output; duplex/filter nodes can have both. `audio.channel` is the canonical per-port channel hint when available; `audio.position` on parent declares layout. `port.id` can order fallback within a node, but `FL`, `FR`, `FC`, `LFE`, `RL`, `RR`, `SL`, `SR`, `AUX0`… have semantic ordering that beats lexicographic sorting (`AUX10` must follow `AUX9`). [WirePlumber assignments](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html#introduction), [audio positions property](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#node-properties), [PipeWire key list](https://docs.pipewire.org/group__pw__keys.html).

## 2. Port kinds, MIDI and video

Classification must happen **per port**, not simply per Node: an effects client can expose audio and MIDI, and a duplex node both directions. PipeWire documents MIDI as `application/control` SPA format with timestamped `spa_pod_sequence` events; this is not PCM and not equivalent to an arbitrary parameter-control port. `format.dsp` is the widespread easy signal: `32 bit float mono audio`, `8 bit raw midi`, `32 bit raw UMP` and, for qpwgraph's video default, `32 bit float RGBA video`. These are **exact observed strings in qpwgraph**, not a comprehensive enumeration of video formats. `media.class` identifies node role (e.g. `Audio/Sink`, `Audio/Source`, `Audio/Duplex`, `Stream/Output/Audio`, `Stream/Input/Audio`, `Video/Source`, `Stream/Input/Video`, `Midi/Bridge`), but a class is neither the port's negotiated format nor proof that every port shares it. Sources: [qpwgraph defaults and registry parser](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L36-L40), [PipeWire MIDI Design](https://docs.pipewire.org/page_midi.html#design), [WirePlumber media classes](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html#introduction).

[INFERENCE] Classification precedence: (1) exact recognized `format.dsp` audio/MIDI1/UMP/video; (2) readable `EnumFormat` POD of the **port** to distinguish `Audio`/`Video`/`Application`+`Control` and supported subtypes; (3) known node `media.class` as a tentative category only when unambiguous; (4) `Unknown`, visible in an advanced inventory but disabled for blind linking. Avoid `contains("Audio")` as sole validation. Collect all `EnumFormat` alternatives if offered; the first enum result is not necessarily the negotiated format. Helvum binds Port, checks readable `ParamType::EnumFormat`, calls `proxy.enum_params(0, Some(ParamType::EnumFormat), 0, u32::MAX)`, parses `parse_format` into `MediaType`, and separately parses Link's actual negotiated `format()`. Its UI classification is broad `MediaType` (does not preserve MIDI1 versus UMP distinction). [Helvum `handle_port_info`, `handle_port_enum_format`, `get_link_media_type`](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L333-L563).

ALSA sequencer: WirePlumber's ALSA MIDI monitor creates a **single SPA ALSA sequencer bridge node** (`Midi-Bridge`/`Midi/Bridge` commonly observed) with ports representing individual MIDI client/streams. This is unlike ALSA audio Device→multiple PCM Nodes: the bridge's PipeWire node name alone cannot group separate keyboards correctly. Port aliases/names can contain `client:port`, human sequencer name such as `Midi Through Port-0`, and bridge-specific `api.alsa.seq.*` identifiers; inspect observed properties rather than hard-coding textual name parsing as primary key. A documented captured graph has `port.group = client_40`, which is useful **if present**, but `client_40` is a runtime sequencer number, not a restart-stable identity. ALSA `Midi Through` virtual ports must not be mistaken for a physical USB MIDI interface. Source: [PipeWire MIDI Implementation](https://docs.pipewire.org/page_midi.html#implementation), [HoustonPatchbay special Midi-Bridge ports](https://raysession.tuxfamily.org/manuals/patchbay/en/manual.html#special-ports), [sample bridge graph with `port.group`](https://gist.github.com/fadeddata/67cb13ed141248a2a8bbabd61bf37256). [INFERENCE] If the installed ALSA MIDI bridge is missing, no such PipeWire ports exist, even though `aconnect` could list sequencer devices.

JACK clients under PipeWire register native graph ports; `client.api` can indicate `jack` / `pipewire-jack`. JACK's ordinary `application/control` port is interpreted as MIDI; qpwgraph labels native MIDI `8 bit raw midi`. PipeWire 1.2's MIDI documentation covers SPA `SPA_CONTROL_Midi`/MIDI1 and legacy JACK conversion; newer 1.4 and 1.6 docs say UMP (`SPA_CONTROL_UMP`) became preferred and legacy consumers get MIDI conversion. A JACK port explicitly `32 bit raw UMP` or `JackPortIsMIDI2` takes UMP events; normal JACK MIDI input gets MIDI1-converted events. **Do not infer that exact-string inequality makes UMP↔MIDI1 impossible**: current qpwgraph explicitly aliases `32 bit raw UMP` to its MIDI1 display port type with comment “FIXME: legacy aliasing,” while PipeWire documents conversion. Nor infer conversion is fully transparent: development/1.7 documentation says preference reverted to MIDI1 because conversions in ALSA and PipeWire are not completely transparent, and UMP ALSA consumers must opt in. Treat mixed-format links as capability-dependent and verify negotiation/resulting Link state. Sources: [PipeWire 1.2 MIDI](https://docs.pipewire.org/1.2/page_midi.html#jack), [PipeWire 1.6 MIDI](https://docs.pipewire.org/page_midi.html#jack), [PipeWire development MIDI](https://docs.pipewire.org/devel/page_midi.html), [qpwgraph `createPort`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L1260-L1297).

Bluetooth **audio** devices are normal BlueZ-created device/nodes with `api.bluez5.*` properties (actual property presence depends on profile). BLE-MIDI is **not** guaranteed to appear simply because the headset is a Bluetooth Device; if a separate BLE-MIDI service exposes an ALSA sequencer client, the bridge can expose it. [INFERENCE] Distinguish this bridge appearance from `device.api=bluez5` audio and show unknown BLE-MIDI hardware origin rather than asserting a direct BlueZ MIDI node. Evidence for BlueZ device configuration and ALSA-MIDI separate monitor: [PipeWire props Bluetooth monitor example](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#customizing-properties), [PipeWire MIDI Implementation](https://docs.pipewire.org/page_midi.html#implementation). `port.monitor=true` marks an output reflecting input to a sink/stream and should be segregated to avoid duplicate-looking channels. `port.control=true` or `port.direction=control/notify` is a special port indicator, **not sufficient to call the port MIDI**; filter/audio-control/CV and MIDI need negotiated format discrimination. [PipeWire port keys](https://docs.pipewire.org/group__pw__keys.html), [audio adapter monitor ports](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#audio-adapter-properties).

## 3. Existing patchbays and CLI behavior

**qpwgraph.** The C++ PipeWire backend creates a `pw_thread_loop`, context/core/registry and watches registry `global`/`global_remove`. It tracks only Node/Port/Link for canvas, binds proxies for detailed info and coalesces `changed()` into a canvas refresh; Device/Client are **not** used as hierarchical grouping keys. A node display name comes from `node.description` → `node.nick` → `node.name` → `node`, optionally prefixed `application.name/`; node nick is retained separately, media name can become a secondary label. Node role/type is inferred from `media.class` substrings and duplex fallback. Port display chooses `port.alias` before `port.name` → `port`, gets parent by `node.id`, media from `format.dsp` (video-class fallback), direction from `port.direction`, tracks physical/terminal/monitor/control flags. Canvas may split source/sink appearances of a duplex node, suffix nonphysical monitor/control names, and uses numbered duplicates of equal `(name, mode, type)` to avoid collision; user merger prefix rules unify selected node labels. Sources: [`qpwgraph_registry_event_global`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L414-L529), [`createNode`/`createPort`/`findNodePort`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L980-L1302), [manual Merger option](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph-user_manual.md#options).

qpwgraph creates link through `pw_core_create_object("link-factory", Link, props)` with four live node/port **global IDs**, `object.linger=true`, optional `link.passive=true` from `PIPEWIRE_LINK_PASSIVE`; validates output→input and equal UI port type. Removal finds the Link global ID and calls `pw_registry_destroy`. qpwgraph links with current IDs and uses a sync/error listener; the factory's `object.linger` keeps created link alive when its proxy exits but does **not** mean hardware/stream restart persistence. [qpwgraph `connectPorts`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L796-L922), [link-factory docs](https://docs.pipewire.org/page_module_link_factory.html#properties-for-the-create_object-call).

qpwgraph's **Patchbay** is a separate saved rule set: activate restores pinned connections; deactivate stops enforcing them (manual describes pinned links being dropped when unchecked); **Exclusive** removes connections outside stored set; Edit Pin/Unpin changes membership, Auto Pin records manual connections, Auto Disconnect disconnects pinned connections on deactivation. Graph layout/renames live in `~/.config/rncbc.org/qpwgraph.conf` independently of connection rules. It also optionally connects native ALSA MIDI via separate ALSA MIDI support: the manual explicitly colors PipeWire/JACK and ALSA MIDI differently; do not confuse its ALSA-layer connections with all being PipeWire Link globals. [qpwgraph patchbay manual](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph_patchbay-user_manual.md), [qpwgraph user manual Ports/Options](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph-user_manual.md#ports), [qpwgraph ALSA MIDI implementation](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_alsamidi.cpp).

**Known qpwgraph pain points relevant to a matrix:** duplicate same-name nodes force synthetic suffixes; a single graph node can become multiple display boxes; exact `format.dsp` and broad `media.class` heuristics risk unknown types; UMP display coercion is marked `FIXME`; late/out-of-order Port/Link globals are dropped by its `createPort`/`createLink` until a suitable parent exists; exclusive persistence can fight session-policy auto-links. These are conclusions from [`createNode`, `createPort`, `createLink`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L1193-L1365), [`connectPorts`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L796-L922) and [Patchbay Exclusive manual](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph_patchbay-user_manual.md#exclusive-button). **[INFERENCE]** They are implementation risks, not a measured qpwgraph defect rate.

**Helvum.** Inspected public source is [knyipab's Helvum mirror](https://github.com/knyipab/helvum), not claimed to be a byte-for-byte copy of latest upstream GitLab. `main.rs` creates `async_channel::unbounded()` for PipeWire→GTK and `pipewire::channel::channel()` for GTK→PipeWire, spawns backend thread and joins on termination. Backend owns PipeWire `MainLoop`, Context/Core/Registry, proxy+listener keepalive HashMap, registry callbacks and a backend ID/state map. GTK graph manager consumes typed `NodeAdded`, `PortAdded`, `PortFormatChanged`, `LinkAdded`, removals, link state/format, connection status; its own `items: HashMap<u32, glib::Object>` maps to graph widgets. Node label favors description→nick→name; port label uses **port.name** (not qpwgraph's alias); media type derives readable EnumFormat instead of `format.dsp`. `toggle_link` uses `registry.destroy_global(id)` or `core.create_object::<Link>("link-factory", properties!{four IDs, "object.linger"=>"1"})`. [Helvum `main.rs`](https://github.com/knyipab/helvum/blob/main/src/main.rs#L20-L122), [`thread_main` and handlers](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L69-L563), [`GraphManager::receive`](https://github.com/knyipab/helvum/blob/main/src/graph_manager.rs#L40-L109). This is the best directly inspected Rust threading template; unlike the proposed matrix it does not use Device hierarchy or distinguish MIDI1/UMP in its `MediaType` messages.

**Other visual conventions.** HoustonPatchbay used by RaySession/Patchance/ Patchichi is JACK-centric: `system` capture and playback boxes, `a2j`/`Midi-Bridge` MIDI boxes, hardware decorations; stereo portgroups inferred primarily from names. It exposes separate audio/MIDI/CV filters and blocks dangerous CV→audio by default. [HoustonPatchbay Manual Overview/Special ports](https://raysession.tuxfamily.org/manuals/patchbay/en/manual.html). Carla's *own engine* offers single-client (all plugins one JACK client), multi-client (one JACK client per plugin), and internal modular patchbay (one plugin canvas group), explicitly distinguishing internal/external routing; therefore “one JACK client equals one physical device” is false. Carla treats audio mono channels, CV and merged MIDI/OSC event ports differently. [Carla Manual Basic Concepts/Engine modes](https://kx.studio/Documentation:Manual:Carla). Catia and QjackCtl's Graph are JACK client/port oriented rather than PipeWire Device-ID grouping [INFERENCE]; verify their current versions before treating their grouping behavior as specification. qpwgraph's manual explicitly describes it as based on QjackCtl and adds its own configurable merger. [qpwgraph user manual introduction/options](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph-user_manual.md). RaySession uses HoustonPatchbay and its explicit `a2j`/hardware treatment; do not duplicate an ALSA sequencer bridge as an independent PipeWire device if it is only a bridge node. [HoustonPatchbay Overview](https://raysession.tuxfamily.org/manuals/patchbay/en/manual.html#overview).

`pw-link -o/-i/-l` lists output/input ports/links; `-m` monitors, `-I` prints numeric IDs, `-v` prints aliases/object paths; `pw-link output input`, `-d output input` or `-d link-id` creates/removes, with lingering default except monitor mode and optional passive mode. `wpctl status`, `inspect`, `set-default` primarily show/control WirePlumber-managed devices/nodes/defaults, rather than substitute for full per-port/per-link matrix; the target route is `pw-link` or registry API. [pw-link manual](https://docs.pipewire.org/page_man_pw-link_1.html), [wpctl manual](https://pipewire.pages.freedesktop.org/wireplumber/man/wpctl.html).

## 4. Implementable matrix grouping and labels

**[INFERENCE] Algorithm**, ordered by certainty; a group is a UI container, never a substitute for original Node IDs:

1. Ingest all globals into `HashMap<GlobalId, Object>` with generation/connection epoch; bind Node/Port/Link (optionally Device/Client/Metadata). Queue unresolved parent/endpoint IDs, retry when parent arrives; remove dependent rendered rows when IDs vanish. Preserve source property dictionaries and typed info changes. Use metadata and Device/Client only as *annotations* to prevent physical misgrouping. Basis: [registry listener API](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/registry/struct.ListenerLocalBuilder.html), [Helvum object handlers](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L165-L232).
2. For nodes having resolvable `device.id`, primary group `(Device, device.id)`, then optional subgroup by `node.name`/route/profile and direction. Example: ALSA card's microphone source, line source and speaker/HDMI sinks are separate nodes but one device **only when their actual `device.id` matches**; HDMI GPU and USB card remain separate if different IDs. Resolve group label by `device.description` → `device.nick` → `device.name` → node label, with bus/serial suffix to disambiguate duplicate descriptions. Use `device.name` (and serial/bus path when known) for cross-run group matching, not global ID. [WirePlumber ALSA card/node model](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html#alsa-configuration), [device properties](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#common-device-properties).
3. If node is known ALSA `Midi/Bridge`, subdivide *its* ports by explicit sequencer client identifier (`api.alsa.seq.*` or `port.group=client_<n>` if present) and then human client label extracted conservatively from alias; keep exact original alias in tooltip. Fallback one group `MIDI bridge / unclassified` per bridge, **not** split blindly on punctuation in names. Sequencer client number is runtime only; stable persistence needs a device name + sequencer client/port name and ambiguity handling. [PipeWire MIDI bridge model](https://docs.pipewire.org/page_midi.html#implementation), [captured client_40 example](https://gist.github.com/fadeddata/67cb13ed141248a2a8bbabd61bf37256). [INFERENCE] A group of several ports can represent one USB MIDI interface even though their PipeWire parent node is the same shared Midi-Bridge as unrelated interfaces.
4. For other nodes with no `device.id`, group by `client.id` **within current connection**, with `application.id`/`application.name` display and stable matching hints. `node.group` is a secondary subdivision/association only when corroborated by same client, not a merge across unrelated clients; `node.link-group` can annotate internally related filter nodes but must not collapse their patchable ports. Leave separate nodes selectable under one app group (e.g. DAW track streams). Without `client.id`, use per-node group; never merge all `Firefox` or all `Midi-Bridge` by the same text. [PipeWire key definitions](https://docs.pipewire.org/group__pw__keys.html), [Carla multi-client/single-client contrast](https://kx.studio/Documentation:Manual:Carla).
5. Node sublabel: `node.description` → `node.nick` → `node.name` → `media.name` → `Node #ID`; for stream UI title optionally show `media.name` secondarily, not identity. Port label inside node: `port.alias` if genuinely informative (qpwgraph), else `port.name` (Helvum), else `Port #ID`; offer both original strings in detail view, strip repeated node prefix **only** for display. [qpwgraph registry parser](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L432-L515), [Helvum `get_node_name` and `handle_port_info`](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L219-L408). [INFERENCE] Do not persist user rename by localized description; save rule against machine identity.
6. Sort groups physically tagged first only as a UI preference, then pinned custom order, natural display name, stable fallback. Within group: device route/node, direction, optional `port.group`, semantic `audio.channel` sequence (FL FR FC LFE RL RR SL SR then numeric AUXn), then numeric `port.id`, then natural `port.name`, finally global ID. Physical and terminal flags annotate but do not imply port media. No hard-coded assumption of only two channels: Pro Audio may expose AUX0…AUXn on multichannel USB interfaces; ordinary stereo exposes FL/FR; HDMI may be 2, 6 or 8 channels; Bluetooth A2DP is typically stereo while HFP is often mono or limited profile, **[INFERENCE]** and profile changes can replace nodes. [ALSA pro-audio profile settings and channels](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#alsa-properties), [WirePlumber ALSA profile management](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html), [audio position property](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#node-properties).

**Stereo collapse [INFERENCE].** Store one row per *real output port* and column per *real input port* in graph state. Derive optional paired visual row/column only when two ports share parent, direction, media kind, `port.group`, compatible base label, and explicit FL/FR (or confirmed 1/2 when channels missing). A collapsed cell maps `(L→L,R→R)` as one atomic **user intent** but executes two separate links and renders `none`/`partial`/`both`/`error` states. Never silently link L→R, collapse a mixed mono/stereo cell, or collapse AUX0/1 merely because adjacent: pro-audio channels can be independent microphone preamps. Reveal original ports on expand. The value of stereo portgroups is established by [HoustonPatchbay manual](https://raysession.tuxfamily.org/manuals/patchbay/en/manual.html#overview); the conservative pairing policy is Aizome-specific.

**Disagreement table.** qpwgraph uses node display name + optional app prefix and alias-first port names, user-configured merger prefixes; Helvum uses node name fallback without app prefix and `port.name`, no Device grouping in inspected backend; HoustonPatchbay uses JACK client (`system`, `a2j`) with inferred stereo portgroups; Carla host can expose each plugin as a separate JACK client or all plugins under one master client depending engine mode. This motivates exposing both physical-device and app/client hierarchy rather than declaring one tool's box boundary canonical. [qpwgraph `qpwgraph_registry_event_global`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L414-L529), [Helvum `get_node_name`/port handler](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L219-L408), [HoustonPatchbay overview](https://raysession.tuxfamily.org/manuals/patchbay/en/manual.html#overview), [Carla engine modes](https://kx.studio/Documentation:Manual:Carla).

## 5. Pages, link legality and WirePlumber policy

**[INFERENCE] Pages**: (1) **Audio** all PCM hardware sources/sinks and app streams/filter/virtual nodes, with monitor-output toggle or subview (monitor ports are real patchable output ports but duplicate input signal visually); (2) **MIDI 1 / event** ALSA sequencer bridge and native/JACK legacy MIDI ports in the *same page* because bridge ports are PipeWire ports that can link to other MIDI/control sequence ports after format negotiation; distinguish bridge-origin visually; (3) **MIDI 2 / UMP** selectable separate page/filter until explicit compatibility is known; offer cross-kind routing with “may convert/lose semantics” confirmation only after supported-format inspection; (4) **Video** cameras and capture/processing streams; (5) **Other/control/CV diagnostic** when recognized but unsupported, non-linkable by default. Do **not** make an independent “ALSA sequencer vs JACK MIDI” link namespace for bridge ports; qpwgraph's optional direct ALSA connection subsystem is exceptional. Grounding: [PipeWire MIDI implementation](https://docs.pipewire.org/page_midi.html#implementation), [PipeWire 1.6 MIDI conversion](https://docs.pipewire.org/page_midi.html#jack), [qpwgraph manual port kinds](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph-user_manual.md#ports), [WirePlumber video classes](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html#introduction).

Legal-action preflight: current output port and input port must both exist and be distinct; reject same direction and confirmed incompatible media families (audio↔video, audio↔MIDI, video↔MIDI); for native MIDI1↔bridge MIDI1 allow if formats intersect; for UMP↔MIDI1 or video subformat differences require inspect `EnumFormat` intersection/negotiation before claiming success. Link factory/server determines final compatibility; display pending then observed Link state/error. The fact that PipeWire generic MIDI uses `application/control` means **control-format ≠ universally MIDI**, and CV can be audio-like signal but hazardous when patched to speaker; do not auto-enable audio↔CV. [Link Factory](https://docs.pipewire.org/page_module_link_factory.html), [PipeWire MIDI Design/JACK](https://docs.pipewire.org/page_midi.html#design), [HoustonPatchbay CV safety](https://raysession.tuxfamily.org/manuals/patchbay/en/manual.html#special-ports), [Helvum `handle_link_info`](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L449-L512). [INFERENCE] Treat absence of an overlapping advertised format as a hard local disable, but treat uncertainty as “try, report server error,” not as a guaranteed link.

WirePlumber auto-links playback `Stream/Output/Audio`→`Audio/Sink`, capture `Audio/Source`→`Stream/Input/Audio`, camera `Video/Source`→`Stream/Input/Video`; configured default target metadata takes precedence then highest `priority.session` suitable target. `node.autoconnect` (or 1.2+ stream-specific counterpart) controls auto-routing; `target.object` on **stream nodes** or metadata requests target by name/serial and runtime metadata can move streams unless `node.dont-move`; `node.dont-reconnect=true` inhibits fallback/relink when target disappears; `node.link-group` prevents automatic self-linking. Manually created `object.linger` link survives creator process exit **while both endpoints survive**; when node/port is removed so is the link; neither link-factory nor `pw-link -L` persists cross-restart routing intent. WirePlumber may recreate its own policy links or move a stream when metadata/default changes, while manual extra links may coexist. Thus changes should be reconciled from observed Link globals rather than assuming successful API call or treating every reappearance as user action. [WirePlumber Linking Policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html), [PipeWire session manager properties](https://docs.pipewire.org/1.6/page_man_pipewire-props_7.html#session-manager-properties), [Link Factory object.linger](https://docs.pipewire.org/page_module_link_factory.html#properties-for-the-create_object-call), [pw-link linger](https://docs.pipewire.org/page_man_pw-link_1.html#connecting-ports).

[INFERENCE] For first release, show current policy links alongside manual links and expose default-target metadata read-only; do not silently flip `node.autoconnect`/`node.dont-reconnect` on arbitrary third-party streams. Persistence, if requested, is a separate **desired-routes reconciler** with explicit enable/disable and duplicate/ambiguous-identity safeguards, analogous to qpwgraph Patchbay; exclusive mode intentionally removes third-party policy links and risks a reconnect loop. qpwgraph's exclusive and Auto Pin/Disconnect semantics are documented [here](https://github.com/rncbc/qpwgraph/blob/main/docs/qpwgraph_patchbay-user_manual.md); the reconnect interaction derives from [WirePlumber policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html).

## 7. Performance and event behavior

A live PipeWire registry is event-driven. Device profile changes can remove and re-create many nodes, their ports and links; app launch/exit changes entire subgraphs; `info` updates and EnumFormat parameter replies can arrive independently of registry creation. Helvum maintains two object maps, emits one message per object/change and can receive links before UI-visible endpoints; qpwgraph inventory rebuilds canvased connections on change. Sources: [WirePlumber ALSA profile node recreation](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/alsa.html#device-properties), [Helvum `PipewireMessage`](https://github.com/knyipab/helvum/blob/main/src/main.rs#L31-L86), [qpwgraph `updateItems`](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L1028-L1121).

**[INFERENCE; sizing target, not observed benchmark]** A multichannel interface with 32 capture + 32 playback ports, several 16–64-channel DAW/client streams, plugin nodes and bridge MIDI ports can yield **hundreds** of ports; a fully rendered 200×200 matrix implies 40,000 potential cells even with only tens/hundreds of real links. This is a capacity scenario, not a claim that an average system has a measured count. Keep sparse `links_by_pair` and index ports by node/group/page, virtualize visible rows/columns, do not allocate a full cross-product or recalculate every cell for each info callback. Process structural changes immediately in the backend model, send compact deltas keyed by IDs, coalesce multiple GUI invalidations to one frame (e.g. ~16–33 ms display scheduling), and maintain pending endpoint maps for out-of-order events. Never delay the graph's own event handling for UI work; preserve link creation/removal feedback and errors per operation. Basis for potential bursts: [registry event handlers](https://github.com/rncbc/qpwgraph/blob/main/src/qpwgraph_pipewire.cpp#L414-L552), [Helvum message fanout](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L165-L563); numerical target and scheduling are **[INFERENCE]**. No published event-rate measurements were established here; instrument real systems before choosing queue caps or thresholds.

## Implementation-ready summary

```rust
// Pseudocode; owned, plain data crosses threads; pw proxies/listeners never do.
type GlobalId = u32;
struct Graph {
    epoch: u64,
    clients: HashMap<GlobalId, ClientRecord>,
    devices: HashMap<GlobalId, DeviceRecord>,
    nodes: HashMap<GlobalId, NodeRecord>,
    ports: HashMap<GlobalId, PortRecord>,
    links: HashMap<GlobalId, LinkRecord>,
    metadata: HashMap<(GlobalId, String), MetadataValue>,
    links_by_pair: HashMap<(GlobalId, GlobalId), Vec<GlobalId>>,
    unresolved: HashMap<GlobalId, Vec<DependentId>>,
}
struct NodeRecord { id: GlobalId, device_id: Option<GlobalId>, client_id: Option<GlobalId>,
                    name: Option<String>, class: Option<String>, props: PropertiesSnapshot }
struct PortRecord { id: GlobalId, node_id: Option<GlobalId>, direction: Direction,
                    kind: PortKind, channel: Option<Channel>, local_port_id: Option<u32>,
                    group: Option<String>, props: PropertiesSnapshot }
enum PortKind { Audio, Midi1, Ump, Video, ControlOther, Unknown }
struct LinkRecord { id: GlobalId, output: GlobalId, input: GlobalId,
                    state: LinkState, negotiated_kind: Option<PortKind> }
enum GroupKey { Device(GlobalId), AlsaSeqClient { bridge: GlobalId, client: String },
                Client(GlobalId), Node(GlobalId) }
```

**[INFERENCE]** On each global/info: merge dictionary and typed info, classify port from `format.dsp` then readable EnumFormat then tentative node class, attach to parent or pending map, derive group via Device ID → sequencer bridge client → Client ID → Node ID, compute labels and sorted channel positions. Pages Audio, MIDI1, UMP, Video, advanced Control/Unknown; expose monitors as audio toggle. Only output→input, compatible format families, and actual negotiated format produce confirmed links; UMP↔MIDI1 is conditional conversion, not automatically forbidden or guaranteed. Each visual stereo cell expands into two actual link requests with partial state. Commands `Connect(output_global_id,input_global_id)`, `Disconnect(link_global_id)`, `Reconnect(remote)`, `Stop` travel on `pw::channel` to a single PipeWire thread; bind proxies and execute factory/destroy there. Backend sends immutable `GraphDelta { epoch, changed_ids, removed_ids, command_result }` to Aizome UI, which coalesces redraws and virtualizes the sparse matrix. Reconnect increments epoch and discards old IDs/proxies; any saved route is matched by stable names plus ambiguity check, never previous runtime ID/serial. This summarizes [PipeWire Registry/Core API](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/registry/struct.Registry.html), [Helvum thread architecture](https://github.com/knyipab/helvum/blob/main/src/pipewire_connection/mod.rs#L69-L230), [Link Factory](https://docs.pipewire.org/page_module_link_factory.html), [WirePlumber Linking Policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html).
